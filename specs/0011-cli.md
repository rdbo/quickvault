## Summary

Defines `qvault`, the QuickVault command-line client: how vaults and entries are
addressed, how unlocking works, every command with its arguments, output
formats, exit codes, and the security rules the CLI must follow. The CLI is
the first client (roadmap phase 1) and a thin layer over `qv-core`.

## Specification

### 1. General

1.1. Binary name: **`qvault`**. Built with `clap`. The crate stays `qv-cli`.

1.2. **Vault selection**, first match wins:
1. `--vault <path>` / `-v <path>`
2. environment variable `QVAULT_PATH` (a path is not a secret)
3. `default_vault` in the config file

If none applies, the command fails with exit code 2.

1.3. **Config file:** `$XDG_CONFIG_HOME/quickvault/config.toml` on Linux
(platform equivalents elsewhere). It holds only non-secret preferences:
`default_vault`, `clipboard_timeout`, `color`. It MUST NOT hold secrets.

1.4. **Unlocking (v1):** every command that needs vault contents prompts for the
master password, unlocks, does its work, zeroizes and exits (0009 §3). Commands
that only read the header (`info`) do not prompt and label those fields
unverified. Unlock validates the complete manifest and external anchor.

1.5. **Locking:** the CLI holds the SQLite lock only while it runs (0004
§1.3). If another process holds it, fail with exit code 6.

### 2. Addressing entries and groups

2.1. **Path:** `Group/Subgroup/Title`, relative to the root group. `/` in a
name is written `\/`.

2.2. **ID:** an entry or group can be addressed by ID, or by an unambiguous
ID prefix of at least 6 hex characters, with the `@` prefix: `@3fa9c1`.

2.3. Titles need not be unique. If a path matches more than one item, the
command fails with exit code 5 and lists the matches with their IDs.

2.4. Trashed items are not matched unless the command is a `trash`
subcommand.

### 3. Secret handling rules

3.1. Secrets MUST NOT be accepted as command-line arguments or environment
variables: they leak through shell history, `ps` and `/proc`. Protected
values are entered at a TTY prompt (no echo), generated (0010), or, for
the master password only, read from standard input (3.2). Notes are A1 assets
(0001) even when not protected: `--notes` takes no value and prompts for
multi-line input ending at EOF. Other A2 values passed as arguments (paths,
titles, usernames, URLs, search queries, `--field` values) are visible to the
process list and shell history; `-i`/`--interactive` prompts for every field
value instead, and the help text says so. Attachment content may additionally
be imported from the explicit regular input file of `attach add` (§4,
Attachments). Paths and optional name/MIME are metadata visible in argv;
attachment bytes never enter argv or environment variables.

3.2. **`--password-stdin`** reads the master password from standard input,
for scripting. It works the same on every platform (e.g. piping from a
system keyring tool). It is the only non-interactive way to unlock.

- The first line is read; one trailing `\n` or `\r\n` is removed, nothing
  else (spaces are part of the password).
- The buffer is zeroized after use, like any secret (0008 §1).
- Since stdin is consumed, commands that would prompt for further secrets
  (e.g. `add` without `--generate`) or values (`--notes`, `-i`) fail with
  exit code 2 when combined with `--password-stdin`.
- If stdin is a terminal, the flag behaves like the normal prompt (no echo).

3.3. Protected values (0003 §5.3) are never printed unless `--reveal` is
given. Without it, `show` prints `••••••••`.

3.4. The CLI MUST NOT open `$EDITOR` or write any plaintext to temporary
files (0004 §5.3). All editing is done through prompts and flags. The
confirmed explicit output of `attach save` is a plaintext export under 0008
§3; it does not permit plaintext temporary files (see §4, Attachments).

3.5. The CLI disables core dumps at start-up and uses the same
memory-hygiene rules as every client (0008 §1).

3.6. **Clipboard:** `copy` places the value on the clipboard marked as
sensitive where the platform supports it (0008 §3), zeroizes VK and all
derived keys and closes the vault, then **stays in the foreground** holding
only the copied value, with a countdown. It clears the clipboard (if still
owned) when the timeout (default 20 s, `--timeout`, at most 300 s) ends, or
immediately on SIGINT, SIGTERM or SIGHUP. Staying in the foreground is also
required on X11, where the clipboard content is served by the owning process.

3.7. **Displayed secrets:** `init` and `recovery show` display the recovery
phrase on the terminal's alternate screen and clear it after a keypress, so it
does not remain in scrollback. `--reveal` output is ordinary output (see
Security Considerations).

### 4. Commands

Phase markers refer to the roadmap (ARCHITECTURE.md §7).

#### Vault

| Command | Phase | Description |
|---------|-------|-------------|
| `qvault init <path> [--name <name>]` | 1 | Create a vault. Prompts for the master password twice (suggests a generated passphrase, 0010 §4.2), shows the **recovery phrase**, asks the user to confirm selected words or skip with an explicit warning. |
| `qvault info` | 1 | Show unverified public header data: vault ID, format, generation, profiles and KDF parameters. With verified unlock (`--full`): name, number of entries/groups, last change. |
| `qvault passwd` | 1 | Change the master password (0002 §3.4). |
| `qvault recovery show` | 1 | Show the recovery phrase again after re-entering the master password (0002 §4.2). Refuses unless stdout is a TTY; uses 3.7. |
| `qvault recovery rotate` | 1 offline / 3 synced | Create a new key generation through the resumable workflow in 0002 §3.5; reapprove trusted devices. Requires typing a confirmation. |
| `qvault recover <path>` | 1 | Forgotten master password: unlock with the recovery phrase (prompted) and set a new master password. |
| `qvault verify` | 1 | Full integrity check: re-hash and authenticate every referenced object, manifest and local head (0004 §3.6). |

#### Browsing

| Command | Phase | Description |
|---------|-------|-------------|
| `qvault ls [<group>] [-r]` | 1 | List groups and entries (title, username, URL). `-r` recurses. |
| `qvault search <query>` | 1 | Case-insensitive search over non-protected data: titles, usernames, URLs, group names. |
| `qvault show <entry> [--reveal] [--field <name>]` | 1 | Show an entry. `--field` prints only that field's value (for scripts; still needs `--reveal` if protected). |
| `qvault totp <entry> [--copy]` | 1 | Print the current TOTP code and the seconds left. The code is printed by default (it is short-lived); the seed never is. |

#### Editing

| Command | Phase | Description |
|---------|-------|-------------|

Options: `--type <hint>` (default `login`), `--username`, `--url`, `--notes` (prompts, 3.1), `-i` (prompt for all values), `--field <name>=<value>` (non-protected only), `--secret-field <name>` (prompts), `--generate` (generate the password with vault defaults or the generator flags of `qvault generate`). Without `--generate`, prompts for the password. |
| `qvault edit <entry> [options]` | 1 | Same options as `add`, plus `--title`, `--remove-field <name>`, `--protect <name>` / `--unprotect <name>`. `--secret-field password` re-prompts the password; `--generate` replaces it. |
| `qvault mv <entry\|group> <group>` | 1 | Move. |
| `qvault mkdir <group path> [-p]` | 1 | Create a group (`-p`: create parents). |
| `qvault rm <entry\|group>` | 1 | Move to trash (0007 §2). A non-empty group needs `-r`. |
| `qvault trash ls` / `restore <item>` / `empty` | 1 | Manage the trash. `empty` asks for confirmation. |

#### Clipboard and generator

| Command | Phase | Description |
|---------|-------|-------------|
| `qvault copy <entry> [<field>] [--timeout <s>]` | 1 | Copy a field to the clipboard (3.6). Default: the entry's `secret` field (the first one, if it has several). |
| `qvault generate [options]` | 1 | Generate without saving. Options mirror 0010: `--length`, `--no-lower`, `--no-upper`, `--no-digits`, `--no-symbols`, `--exclude-ambiguous`, `--exclude <chars>`, `--words <n>`, `--separator <c>`, `--capitalize`, `--pin <n>`. Prints the value and its entropy; `--copy` copies instead. Needs no vault (uses vault defaults if one is selected). |

#### Attachments

| Command | Behavior |
|---------|----------|
| `qvault attach add <entry> <file> [--name <name>] [--mime <mime>]` | Read a regular file, at most 10 MiB, and create a new attachment record owned by the live entry. Name defaults to its UTF-8 basename, MIME to `application/octet-stream`. No type sniffing. Report its `@id`, never contents. |
| `qvault attach ls <entry>` | List current attachment IDs, names, MIME and byte sizes. Surface conflicts explicitly. No contents or content hashes. |
| `qvault attach save <entry> <attachment> <path>` | Confirm plaintext export, verify complete content, then stream into a new owner-only regular file at the exact explicit path. Never derive output directories/names from stored metadata; never overwrite. |
| `qvault attach rm <entry> <attachment>` | Confirm permanent attachment removal; commit a minimal causal tombstone and drop its retained payload/history references. Release chunks only when no retained reference needs them. Explain independent-copy/secure-erasure limits. |

Attachment content may be imported only from the explicit regular input file of
`attach add`; this extends §3.1. Paths, name/MIME and addresses are metadata
visible in argv; bytes never enter argv/environment. `attach save` is explicit
plaintext export under 0008 §3 and an exception to §3.4 only for the confirmed
output file. Plaintext temporary files remain forbidden. Save and rm require
confirmation; `--yes` is explicit script consent. With `--password-stdin`,
save/rm require `--yes`; incompatible combinations fail before unlock.

Attachment addresses are exact names or `@` IDs/prefixes (at least six hex
characters), scoped to the addressed entry. Absent matches fail 4; ambiguity
fails 5 and lists escaped matching IDs. Trashed entries and finally deleted
attachments are unavailable. Conflicted entries block add/save/rm with 8;
conflicted attachments block save/rm with 8. Listing emits each live metadata
head separately, without combining conflicting values.

Only ls accepts `--json`: an array of objects with `id`, `version_id` (32
lowercase hex each), `name`, `mime`, `size` (integer bytes), `conflicted`
(boolean), sorted by attachment ID then version ID. No contents or content hash
are listed. Other attachment commands reject JSON before unlock. Save sends no
content to stdout and reports success only after full verification/file sync.

Input/output paths reject symlink components, `..`, invalid final components
and nonregular files. Held directory descriptors anchor no-follow traversal;
existing ancestors must be owned by effective UID or root and not writable by
other users (no sticky-directory exception). Output is exclusively created,
owner-only (0600), at the exact explicit path, never from stored metadata.
The input is opened once and checked for identity/size/time changes while
reading; same-size concurrent edits cannot be proved absent, so import hashes
and encrypts the bytes actually read. No automatic MIME sniffing or opening.

Save confirms and verifies complete content before output creation, then streams
a second authenticated read with complete length/hash checks. Failure or crash
may leave incomplete plaintext at the explicit destination; report incomplete
output on handled failures. Do not unlink through a mutable path or claim secure
erasure. Never overwrite an existing path. Core streaming sinks can receive
individually authenticated chunks before complete-content validation; partial
output is never success. Failed saves do not mutate vault state.

Attachment errors retain §6: absent 4, ambiguity 5, conflict 8, size bound 9,
integrity 7, invalid options/metadata 2, I/O/unsafe path/existing output 1.
Cancellation is 1; existing store/anchor mappings apply. Errors omit contents.

#### History and snapshots

| Command | Phase | Description |
|---------|-------|-------------|
| `qvault history <entry>` | 1 | List previous versions: date, device, which fields changed, conflict flag. |
| `qvault history show <entry> <version> [--reveal]` | 1 | Show an old version. |
| `qvault restore <entry> <version>` | 1 | Restore an old version as an explicit new causal edit (0007 §1.5). |
| `qvault snapshot ls` / `restore <id> <path>` | 1 | List local snapshots; restore imports the archive into a **new** vault file and requires an explicit new recovery baseline. |
| `qvault history purge <entry>` | 1 | Suppress and purge eligible history (0007), keeping unresolved versions and tombstones. Confirmation required; report remote acknowledgements and independent-copy limits. No secure-erasure claim. |

History commands use these milestone-1 contracts. `history <entry>` lists
retained dominated versions newest first by `(modified_at, version_id)`, with
version ID, date, writer components, changed-field metadata and current conflict
status; it does not list active heads. `history show` and `restore` address a
retained version by its full ID or an unambiguous six-or-more-hex prefix,
optionally with `@`, scoped to the addressed entry. Invalid syntax is exit 2,
absent or suppressed history is 4, and ambiguity is 5 with matching IDs. Writer
vectors are displayed as IDs and counters; no device attribution is invented
when none is authenticated.

Changed fields are compared with the current browsing representative and are
labelled with `compared_to`; old/new values are never included in history lists.
Protected values remain masked unless `--reveal` is explicitly supplied to
`history show`. Unknown optional payload differences are reported as unknown
extension changes. Historical handles cannot be used for copy, TOTP or generic
current-field reveal.

`restore <entry> <version> [--resolve-conflicts]` creates a fresh causal version
joining all known current heads. If the entry has multiple heads, it fails with
exit 8 unless `--resolve-conflicts` is supplied. The selected historical entry
payload and unknown extensions are restored as a new version with the current
modification time; creation time, current live/deleted state and the live
historical group are preserved. Attachments are separate records and are
unaffected. An unavailable destination group fails without an edit; unseen
concurrent edits are not implicitly resolved.

`history purge <entry>` requires confirmation (or explicit `--yes`) and advances
the local suppression floor to the join of all currently known heads while
preserving active heads, conflicts and permanent tombstones. It reports that
unseen concurrent history, snapshots and independent copies may remain and that
no secure erasure is promised. With `--password-stdin`, confirmation operations
require `--yes` before unlock. Read history/show accepts `--json`; restore/purge
reject it before unlock. JSON contains IDs, timestamps, writer vectors,
conflict/comparison metadata and changed names only—never values or content
hashes. Existing exit mappings remain: integrity 7, restore conflict 8, bounds
9, cancellation/I/O 1.

History-list JSON is `{ "versions": [...] }`. Rows contain `version_id`
(32 lowercase hex), `modified_at` (RFC3339), `device` (null without authenticated
attribution), `writers` (array of `{id,counter}` sorted by writer ID), `conflict`
(boolean), `compared_to` (32-hex ID), `changed_properties` (sorted fixed labels),
`changed_fields` (array of `{id,name}` sorted by field ID; removed fields use
their old name), and `unknown_extensions_changed` (boolean). Compare complete
fields, including order, presence, kind, name, protection, value and optional
extensions. Historical-show JSON follows `show`, with `version_id` identifying
the selected historical version; masked protected values are null. Display all
stored names escaped in human output. History listing and mutations use ordinary
entry addressing, so trashed entries do not match. No server purge acknowledgement
applies in the offline implementation. Cancellation and unavailable restore
groups are exit 1; stale handles/changed files are 6. Errors omit payload values.

#### Snapshots and verification

- **`qvault verify [--json]`** — requires unlocking the selected vault. It
  re-hashes every referenced object, authenticates the manifest, every active
  head, every retained history version and every attachment chunk (0004 §3.6),
  and reports the local head and the external anchor comparison. It never
  mutates the vault and never repairs it. It unlocks with the recovery-anchor
  semantics, so a vault whose anchor is missing or mismatched is still
  checked and reported rather than refused before the report exists.
  Human output is one line per check group plus a summary line; JSON is
  `{"vault_id","key_generation","local_seq","anchor","objects","records",
  "active_heads","retained_versions","tombstones","total_bytes","ok","notes"}`,
  where `anchor` is `"verified"|"advanced"|"missing"|"mismatch"`, counts are
  integers, `notes` is an array of fixed-label strings (for example
  `"suppression-floor-covers-dominated-versions"`) and no object ID, hash,
  record ID, payload or path appears. Exit 0 when every check passes and the
  anchor is `verified` or `advanced`; 7 for any integrity failure (missing or
  mismatched object, length, hash, AEAD, manifest, head, anchor); 3 wrong
  password; 6 locked or changed on disk; 9 over a bound; 1 otherwise
  (including cancellation).
- **`qvault snapshot ls [--json]`** — requires unlocking the selected vault (it
  authenticates each snapshot header with the vault key) and lists only local
  snapshots of that vault ID and key generation, newest first by authenticated
  `created_at` and then archive ID. Rows: `id` (32 lowercase hex archive ID),
  `created_at` (RFC3339), `kind` (`"ordinary"` or `"recovery"`), `size`
  (bytes on disk), `objects` (integer), `total_bytes` (referenced ciphertext).
  JSON is `{"snapshots":[…]}`. Files in the snapshot directory that cannot be
  authenticated, belong to another vault or generation, or carry a password
  slot are reported as warnings on stderr and never appear as rows, so one
  damaged file cannot hide the healthy ones; that case does not change the exit
  code. Exit 0; 3/6/9 as above; 1 for I/O.
- **`<id>`** in `snapshot restore` (1.13b) is a full 32-hex archive ID or an
  unambiguous prefix of at least six hex characters, with optional `@`.
  Invalid syntax 2; absent 4; ambiguous 5 with the matching IDs; an archive of
  another vault or generation, or one carrying a password slot, is 7 when the
  header cannot be authenticated with the available vault key.
- **Snapshots and destructive operations (0007 §3.2–3.3).** `trash empty`
  writes and verifies a recovery snapshot before its deletion commits. If the
  snapshot does not fit the ordinary budgets it reports the required space and
  asks for explicit approval to exceed them (`--yes` gives that approval);
  declining aborts the deletion with exit 9 and no change. If the snapshot
  cannot be written at all (disk full, unsafe directory), the deletion is
  aborted with exit 1 and nothing is purged. After the deletion commits the copy
  becomes an ordinary snapshot subject to pruning. Soft deletes (`rm`,
  `trash restore`) and `attach add` take no snapshot.
- **Ordinary snapshots are automatic policy, not user actions.** An unlock may
  take at most one ordinary snapshot per hour and one on the first unlock of a
  day (0007 §3.2). Snapshot failures and budget skips never fail the requested
  command and never touch stdout; they are warnings on stderr.
- With `--password-stdin`, the confirmation and budget question of
  `trash empty` require `--yes` before unlock, as for the other destructive
  commands. Read commands reject nothing new; `snapshot restore` rejects
  `--json` before unlock.

#### Sync and later

Local vault commands require no account or network configuration. LAN and
remote sync are independently optional and initially manually initiated
(0005 §0.5). Local commands, unlock and login MUST NOT start a sync round or
schedule background retries. The `…` entries below reserve command
families, not final subcommands or argument syntax; the corresponding protocol
amendment must specify them before implementation. Pairing secrets MUST NOT be
passed in argv, environment variables, URLs in logs or command history (see §3).

| Command | Phase | Description |
|---------|-------|-------------|
| `qvault merge <archive.qvsnap>` | 2 | Authenticate a private copy of an immutable same-generation archive and causally merge complete record versions (0005 §4). |
| `qvault lan …` | 2 | Link approved same-network peers and initiate direct sync without an account/server/Internet access (0005 §6). Exact pairing/addressing/subcommands await the LAN protocol decisions. |
| `qvault account …`, `qvault device …` | 3 | Optional remote account setup and server device enrollment/revocation (0006); no prerequisite for local or LAN use. |
| `qvault sync` | 3 | Initiate remote sync for the selected vault from any authorized enrolled device (0005 §3). Does not imply LAN sync; exact remote arguments remain part of the protocol work. |
| `qvault snapshot export <directory> [--self-contained]` | 2 | Publish an immutable archive under a new unique name (0004 §6). By default it has no password slot and opens only with VK (another device of this vault or the recovery phrase). `--self-contained` adds the password slot after a warning about offline guessing by whoever holds the file. |
| `qvault conflicts [<target>] [--reveal]` / `qvault resolve <target> --version <version>` | 2 | Inspect all record kinds and explicitly select a complete active version for a new causal edit covering all inspected heads. Exact contracts below. |
| `qvault checkpoint show` / `compare <checkpoint-file>` | 3 | Export/compare the remote (sequence, checkpoint ID) per 0005 §5.5; never report global freshness from a successful sync alone. |
| `qvault import …`, `qvault export …` | later | Third-party/plaintext formats need a separate specification. |

**Archive command contracts (0028):**

- `merge <archive.qvsnap> [--allow-over-budget]` authenticates a bounded private
  copy, then takes a verified pinned recovery snapshot while serializing the
  session through acceptance. No snapshot or an unapproved budget overrun aborts
  before acceptance. The flag explicitly permits the necessary recovery copy
  to exceed ordinary budgets; `--yes` alone does not. The normal budget/anchor,
  input, integrity and cancellation error codes in §6 apply. Identical receipt
  redelivery creates no new local commit. Imported conflicts and working local
  password slots are preserved.
- Merge prints `local acceptance: committed` or `local acceptance: already
  accepted`, then `conflicts: N` (all record kinds). Successful acceptance exits
  0 even when conflicts remain. This is neither resolution, peer receipt nor
  proof of freshness. If acceptance is durable but anchor completion fails,
  print the acceptance outcome first, then the fixed error with its usual exit
  code. A precommit failure prints no successful acceptance.
- `snapshot export <directory> [--self-contained]` publishes
  `<random-32-lowercase-hex>.qvsnap` without replacement and prints its ID. The
  destination must be private and separate from the configured snapshot
  directory; create it with owner-only permissions if absent. The default has
  no password slot. With `--self-contained`, warn that anyone holding the file
  can try offline master-password guessing, then require confirmation. Explicit
  `--yes` may skip that confirmation; it never adds a slot without the flag.
  Refusing confirmation exits 1 without publication. An unsafe destination,
  failed verification or publication uses the existing §6 error mapping.
- Both commands reject `--json` with exit 2 before unlock. Signal/session lock
  cancellation is checked before acceptance/publication. Once committed or
  published, report the actual outcome rather than claiming cancellation undid
  it. Published files and the mandatory recovery copy are never deleted merely
  because an import failed. No network activity or background retry is started.

**Conflict command contracts (completion of 0028):**

`conflicts [<target>] [--reveal]` supports `--json`. With no target it lists
all conflicted records, including groups, vault metadata, attachments and
password keyslots: record ID, kind and head count. JSON is
`{"conflicts":[{"id":hex,"kind":name,"versions":count},...]}`. `--reveal`
requires a target (usage 2 before unlock). A target is an existing entry/group
path or `@` plus a 6–32 hex record-ID prefix; explicit IDs reach every kind,
including tombstones and records in trash. Missing/ambiguous IDs use 4/5.

With a target, stream each active version independently, sorted by version ID.
JSON is `{"record_id":hex,"versions":[...]}`. Each version has `version_id`,
`kind`, `state` (`live`, `soft_deleted`, `final`), `modified_at`, `clock` (sorted
`[writer_hex,counter]` pairs), `unknown_extensions` and typed `details`.
Entry details include the complete known metadata and field list as in `show`;
protected field values are null with `protected:true` unless explicitly revealed.
Group details include parent/name/notes/icon/order/deletion; vault metadata
includes name/description/root/settings; attachment details include owner/name/
MIME/size/chunk count, never contents/content hash. Keyslot details contain only
slot ID and KDF/wrap profile IDs: salts, commitments, nonces, wrapped keys and
unknown descriptor values MUST NOT appear, even with `--reveal`. Unknown optional
values are indicated rather than interpreted or dumped. Human output conveys
the same choices, escapes all stored text and masks protected values. Inspection
alone does not mutate or resolve a record.

`resolve <target> --version <6–32-hex-version-prefix>` (optional leading `@`)
selects one complete active version and creates a new edit joining all heads inspected for that
choice. Preserve protected/TOTP values and unknown optional fields together;
there is no automatic field merge. A stale session or changed head set aborts
(exit 6); a later unseen version may still conflict. Confirmation explains that
boundary; `--yes` may skip confirmation. Selecting a final entry tombstone also
finalizes its owned live attachments atomically, but refuses an affected
attachment conflict (8) until it has been explicitly resolved. Ordinary edits
still refuse unresolved conflicts. Attachment resolution copies verified content
into fresh encrypted chunk objects for the deliberate new version, preserving
retained history and bounded streaming.

A keyslot choice always separately prompts for the selected slot's master
password on the TTY, even with `--yes`. It is never supplied in argv, environment
or an additional unframed stdin line. Verify its pinned KDF/commitment/AEAD and
confirm the unwrapped VK against the current authenticated vault before installing
that complete descriptor. Wrong password uses 3, a foreign VK uses 7. The new
causal slot record, operational slot, header MAC, head and anchor use the existing
atomic write path. Until that explicit proof succeeds, keep the working slot.
Selecting an unconflicted received slot is also an explicit new causal edit.

Resolution rejects `--json` and malformed version prefixes before unlock (2).
Print `local resolution: committed` and `conflicts: N` after a durable commit;
if anchor completion fails print that actual outcome before the mapped error.
A precommit error/cancellation prints no successful resolution. These commands
claim no global freshness, unseen-version resolution or erasure of independent
copies.

For local `snapshot restore`, an ambiguous slotless snapshot uses the source
session's authenticated working password slot in the new baseline, preserving
all snapshot heads. Unlock has reauthenticated that working slot; no incoming
slot is chosen or conflict resolved. The CLI explains this fallback when reporting
which password unlocks the restored copy. A single-head snapshot and an explicitly
self-contained backup keep their existing slot rules.

LAN and remote sync commands remain foreground operations under §1.4: unlock,
perform the requested operation, then zeroize and exit. Bounded retries may
occur within that command; pending changes after exit wait for the next explicit
sync command. No background sync daemon is introduced here. An explicit local
commit must be reported separately from
confirmed peer receipt or server publication; failure to reach a sync endpoint
does not undo a successful earlier local edit. Checkpoint commands concern
server state only; LAN sessions do not allocate server sequences.

### 5. Output

5.1. Human-readable by default; colour only when stdout is a TTY and
`NO_COLOR` is unset.

5.2. `--json` on read commands gives stable, documented JSON for scripting.
Protected values appear only with `--reveal`; otherwise the key is present
with value `null` and `"protected": true`. The JSON of `verify` and
`snapshot ls` (§4 *Snapshots and verification*) follows this rule and carries
no object ID, hash, record ID, payload or path.

5.3. Errors go to stderr. Messages MUST NOT contain secret values. Escape
control characters in all human-readable vault text and errors, including ANSI
and OSC sequences; JSON uses standard JSON escaping. Render neither terminal
commands nor clipboard control sequences from stored content.

5.4. **Weak master password** (`init`, `passwd`, `recover`): the CLI follows
0010 §4.2. Below the "Weak" threshold it prints the warning, waits 5 seconds,
and only then asks `Create the vault with this weak password anyway?
[y/N]`. `--yes` does **not** skip this.

5.5. Destructive commands (`trash empty`, `history purge`, `recovery rotate`,
`attach rm`) and plaintext attachment export (`attach save`)
ask for confirmation; `--yes` skips it for scripts, except `recovery rotate`,
which always requires typing the confirmation.

### 6. Exit codes

| Code | Meaning |
|------|---------|
| 0 | Success |
| 1 | Other error |
| 2 | Usage error / no vault selected |
| 3 | Wrong master password or recovery phrase |
| 4 | Entry, group, attachment or vault not found |
| 5 | Ambiguous path (matches listed on stderr) |
| 6 | Vault locked by another process, or changed on disk during the command |
| 7 | Integrity/rollback failure: authentication, completeness, anchor or remembered checkpoint validation failed |
| 8 | Unresolved conflict: explicit version choice/resolution required |
| 9 | Resource or safety policy limit exceeded; accepted data unchanged |

## Security Considerations

- `--reveal` output stays in terminal scrollback and may be captured by
  terminal logging; the help text says so.
- Entry paths and non-protected values given as arguments are A2 data exposed
  to the process list (other local users can read `/proc/*/cmdline` unless
  `hidepid` is set) and shell history; `-i` avoids this.
- A `--vault` path in a file-sync folder is warned about (0004 §1.1).
- `--password-stdin` lets scripts unlock; protecting where the password comes
  from (e.g. not `echo`-ing it from a script file) is the script author's
  job. The help text recommends piping from a keyring tool.
- Per-command unlocking costs one Argon2id run (≈ 1 s) per command. That is
  the price of having no long-lived unlocked process in v1.
