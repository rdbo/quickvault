# QuickVault 1.2.1

The app gets a new engine room: the Dioxus renderer is replaced by Tauri 2
with a Leptos page in WebAssembly, on Linux, Windows and Android. On top of
that, two-factor codes are easy to set up and use, every vault on a phone
can have its own fingerprint unlock, and lists scroll as one list. Formats
are unchanged: 1.2.1 opens and writes the same vault, archive and snapshot
formats as 1.0.0–1.1.1 (spec 0015).

**Why 1.2.1:** 1.2.0 was tagged, but its release build failed in Android
lint (a check in the lifecycle library crashes lint's release pass), so
1.2.0 was never published. 1.2.1 is 1.2.0 with that check disabled; this
record covers everything since 1.1.1.

This file is the release record that 0012 §3 asks for. Everything in the
[1.0.0 record](1.0.0.md) about signing, build inputs, the security status
and known limitations still applies; this file lists only what changed and
what was checked for it.

## What changed (plans 0070, 0071)

- **No local server any more.** Dioxus sent every screen update over a
  websocket on a loopback port, and attachment previews over a second
  loopback listener. The app now runs fully in process: nothing listens on a
  socket. The connection whose drops 1.1.1 had to work around (a screen
  that stopped reacting after a quick app switch) no longer exists.
- **How screens reach the page.** Rust builds each screen as a frame; the
  page renders it and sends typed actions back through one bounded command
  (64 KiB, strict decoding). The page never sees vault handles: it gets
  random references that a lock clears. Previews stream over an in-process
  scheme, at most 64 KiB per response, revoked on close, lock and hide.
- **Webview hardening carried over.** Strict CSP (no inline script), exact
  navigation checks, no new windows, downloads or developer tools, and an
  incognito webview. On Linux the context menu still appears only in text
  fields (Paste, Delete, Select All), and permission, file-chooser and
  sign-in prompts are refused. On Windows, browser shortcuts (reload, find,
  print) do nothing in the app.
- **Android** keeps its application ID, signing key and version-code rule
  (1.2.1 → 10201), so it updates over 1.1.1 with its data. The app's
  classes moved from the leftover `dev.dioxus.main` package to
  `org.quickvault.app`, so Android turns the QuickVault autofill service
  off on this update: select it again once in the system's autofill
  settings. Back still closes menus and screens first.
- **Nothing vendored.** The patched `dioxus-desktop` copy in `third-party/`
  is gone; every dependency comes from crates.io at an exact version.

Specs 0003 §6.4, 0008 §1.1/§4, 0009 (client table, §1.8, §4, §6) and
0012 §1 were amended for the new renderer; see their changelogs.

## Two-factor codes (plan 0073)

- Logins have a **Two-factor code** row with **Set up**: scan the site's QR
  code (Android), type the setup key as the site prints it, or paste an
  `otpauth://` link. The sheet shows the current code at once, which sites
  ask for to finish setup; **More options** covers digits, period and
  algorithm.
- The entry view shows the current code without a reveal ("123 456") with a
  ring for its period; the setup key never shows. A row's right-click menu
  and copy menu copy the current code.
- A pasted `otpauth://` link in "What are you saving?" starts a login named
  after the site. Codes are stored as before (no format change).

## Fingerprint unlock per vault (plan 0074)

- Each vault on a phone can have its own fingerprint (or screen-lock)
  unlock, up to 16. Turning it on for one vault no longer turns it off for
  another. Each has its own key, seven-day limit and three failed attempts;
  turning it off, a password change or removing the vault from the list
  ends only that vault's. A restart of the phone still ends them all.
- Updating from 1.1.1 keeps an existing enrollment: the phone's
  quick-unlock state file (device-local, outside the frozen formats) moves
  to version 2 and version 1 is still read. "Turned off" is now remembered
  per vault, so a vault where it was turned off may offer it once more.

## Owner feedback (plan 0072) and fixes

- Item, trash and conflict lists scroll as one list (the next page loads as
  the end comes into view, up to 1,024 rows at once).
- The new master password shows its strength while you type. Join and sync
  codes have Show/Hide. Scanning a join code on a new install joins once the
  protection review is acknowledged. Notices and the sync receipt fade out.
- Fixed: images over 64 KiB opened to an empty viewer; a desktop video jump
  to an unbuffered position blanked the picture; a row menu near the end of
  the list opened out of view; revealing an empty password kept showing the
  mask; notices covered an open menu.
- Fixed: on a phone, a correct master password could fail with "The vault
  operation could not be completed" right after switching vaults, until a
  restart. The locked screen checked fingerprint unlock by opening the
  vault file on every refresh, which briefly locks it; it now reads the
  vault's ID once per file version.

## Build inputs

- Toolchain: Rust 1.98.1 (`rust-toolchain.toml`), unchanged; the page also
  needs the `wasm32-unknown-unknown` target.
- Tools: wasm-bindgen-cli 0.2.129 (builds the page) and tauri-cli 2.12.4
  (Android), both pinned in CI.
- Dependencies: Tauri 2.12.5 and Leptos 0.8.23 replace Dioxus 0.7.10. The
  dependency record, with the exact licence exceptions, two
  unmaintained-crate advisories and why they do not apply, and 204 new
  `cargo vet` exemptions (development audit debt), is
  `plans/0071-tauri-leptos-migration/DEPENDENCIES.md`.
- Vendored: nothing (the `dioxus-desktop` fork was removed).

## Review status

Plans 0071–0074 have had no fresh-context review. 0071 replaces the webview
bridge, the preview transport and the Android packaging; 0073 handles
two-factor secrets; 0074 changes how fingerprint-unlock keys and their
state are kept and removed. The owner decided on 2026-11-21 to release
without these reviews and without the remaining attended phone checklists
(`docs/RELEASE.md` "Before tagging" item 4). No independent security audit
has been done.

Known issue found on the phone with plan 0071: an unlock started within
about half a second of a lock can fail with "The vault operation could
not be completed"; trying again a moment later works. The previous
session still held the vault's lock. A fix needs its own storage plan.
A related failure after switching vaults (the locked screen opening the
vault file on every refresh) is fixed in this release; whether that also
explains this one has not been re-tested.

Not run locally for this release: the other Android instrumentation tests
(autofill, QR, media, import, fingerprint), an APK signed with the project
key, native
Windows tests and WebView2 behaviour, attended device checklists and real
two-device LAN checks. CI runs the Windows job and the supply-chain job.

Tests and reviews do not establish security.
